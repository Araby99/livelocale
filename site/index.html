What the video shows

Tidewell is a fictional demo site; the Studio and the pull request are real.

  1. The Tidewell pricing page is open in the livelocale share Studio. Its headline has a typo: “Plans that grows with you”.
  2. The headline is picked: Alt+Click on a computer, a tap on a phone. The editor opens on the key hero.title; “grows” is changed to “grow” and saved.
  3. The locale is switched to Arabic and the page turns right to left. The “Start free trial” button has no Arabic yet; it is picked the same way, and ابدأ تجربتك المجانية is typed and saved.
  4. Send to developer: credited to Lina, it lists both changes and the change link, with Open on GitHub.
  5. The real pull request #2 on GitHub, opened by the livelocale workflow, applies both changes; its files show the two JSON diffs.

Not an i18n library. next-intl or react-i18next keeps the routing, locale detection and formatting; livelocale only changes how text gets fixed.

When you ship the site

  1. 1

    Install it and run init

    One dependency, with no dependencies of its own. init sets up a Next.js app; on Vite you add the plugin, on Astro the integration. init --share adds share links for any static host and, on GitHub, the workflow that turns them into pull requests. 

    $ npm i livelocale
$ npx livelocale init

# share links on any static host, plus the GitHub workflow
$ npx livelocale init --share
  2. 2

    Your team fixes the text. You review a pull request.

    Whoever spots the wrong text fixes it on the site and presses Send. You get a pull request in your own repository, with every change as a JSON diff. This one is real: pull request #2 in Araby99/tidewell.

  3. 3

    CI catches what was never translated

    npx livelocale check --hardcoded runs in GitHub Actions or any CI and fails the build on text that never went through translation.

    Here it read a cut of the Tidewell pricing hero: the demo button was typed straight into the JSX and the Arabic note was left in English, so it exits 1 before either ships.

    It reads JSX and Astro templates, not page metadata or text built at run time. What it does not see

When you fix the text

  1. 1

    Open the link your developer sent

    It opens the real site with the Studio around it. No account, no git, nothing to install.

    Working with a freelancer or an agency? Same link: you fix your own copy, and they review a pull request.

  2. 2

    Hold Alt and click the wrong text

    The editor opens on that exact string, showing the text it will replace. Type the fix in any locale: switch the locale to Arabic and the page turns right to left, and ابدأ تجربتك المجانية goes into the button that had no Arabic yet.

    Can’t find the text on the page? Search the Texts list and pick it: the page scrolls to the text and outlines it.

  3. 3

    Press Send. That is the whole job.

    Type your name, and Send lists every change you made, the old text struck beside the new, with one link. Paste it to your developer; on GitHub it opens their pull request. You never touch git.

Edit every language your site speaks

One page, every locale, fixed in place. Pick French, German or Japanese in the Studio’s Language menu and the page shows that text, ready to edit. Pick Arabic or Hebrew and a site that lays itself out right to left flips under the Studio, which stays in English.

Questions developers ask

Does anything ship to production?

livelocale is on only when NODE_ENV is development, or when you switch preview mode on with LIVELOCALE=preview. In a production build there are no watermarks, the mutation API refuses every request and the in-page client stays off. Read about the safety switches

Is it secure?

In development the mutation API takes writes only from localhost and the origins you allow, only as JSON, and only inside your locales folder. A share link holds no credential: a leaked link only proposes text, and a person still merges the pull request. Read how it is secured

We don't use GitHub. Does it work?

Yes. In development the Studio writes to the locale files on your machine, so any git host works. For a share link, npx livelocale apply "<link>" --pr commits the fix on a new branch with your own git login and pushes it, ready for a pull or merge request. Share links on other git hosts

Is it an i18n library?

No. livelocale sits on top of next-intl or react-i18next, and your library keeps doing the routing, locale detection, date and number formatting and message rendering. livelocale only changes how text gets fixed: on the real site, landing in your JSON locale files. Pick your stack in the docs

Which i18n libraries does it work with?

Keep next-intl or react-i18next: wrap the t you already have with wrapTranslationEngine. In Server Components and Astro pages, createTranslations loads your JSON locale files directly. Pick your stack in the docs

Does it work with a static export?

Yes. For Next.js output: 'export', livelocale build --preview -- next build watermarks the pre-rendered pages and packs the Studio into the build (on Astro, -- astro build). Deploy that build to a staging location, not to production. Read the build reference

What does it cost?

Nothing. livelocale is free and open source under the MIT licence, with no account to make and no server to run. Read the licence

Is my content sent anywhere?

Not by livelocale: there is no livelocale server and no analytics. In development the Studio talks only to your own dev server; on a share link, fixes stay in the person’s browser until they send you a change link. The share link’s manifest is public, though: it lists every string and key name. What a share link makes public
