# livelocale 1.0: API audit

Date: 2026-11-08. Branch: `release/1.0.0`. Starting point: livelocale 0.12.1 plus the unreleased
phone work.

This is the review of everything people can depend on, done before the version number says
"stable". Four areas were checked, and each finding was re-checked by a second reviewer: the
JavaScript imports, the CLI and configuration, the data formats that travel between versions
(share links, the share folder, the Studio-to-page messages), and the supported environments.

## 1. What 1.0 promises, in plain words

Before 1.0, semantic versioning lets a project break things in any minor release (0.12 to 0.13).
From 1.0 on the rule changes:

- **1.0.x (patch):** bug fixes only.
- **1.x (minor):** new things can be added. Nothing documented is removed or renamed, and nothing
  documented starts behaving in a way that breaks a working setup.
- **2.0 (major):** the only place where something can be removed or renamed.

That is what "freezing" means: the names and behaviours in section 2 are what 1.x keeps working.
It is why the audit happens now. Removing or renaming something is free at the jump from 0.12 to
1.0, and costs a 2.0 afterwards. Adding things stays free forever, so anything not decided today
can still be added later.

A 1.0 also tells a team picking a tool that upgrades will not break their build. "1.0, now on
phones" carries that message; "0.13" does not.

The one promise that matters most is the share link. A change link someone already sent
(`lc1.…`) and a share folder already on someone's host must keep working in every 1.x. Section 4
covers how that is now tested.

## 3. Changes recommended before 1.0

### 3.1 Non-breaking: applied on this branch

1. **Stability page** `site/docs/reference/stability.md` ("Versioning and stability"), in the
   Reference sidebar: what semver covers, what is internal, the share-link promise, the
   deprecation policy (deprecate in a minor with a warning, remove only in the next major) and
   the versions CI tests.
2. **README:** a "Supported versions" table and a link to the stability page.
3. **`@internal` tags** on the 22 undocumented exports listed in 2.1. Nothing removed.
4. **Doc comment fixes:** `sanitizeZeroWidth` pointed users to `stripWatermark` (now `unwrap`);
   `createTranslations` claimed a "type-safe" result (it returns `Record<string, any>`);
   `hasWatermark` claimed a full check (it checks one character); `allowedOrigins` had no doc
   comment; `fetchImpl` was described as "for tests".
5. **Share links guide:** "any browser" became "a current Chrome, Edge, Firefox or Safari".
6. **Compatibility fixtures** under `tests/fixtures/compat/0.12.1/` and the test
   `tests/unit/compat-0.12.1.test.ts` (section 4).
7. **Major changeset** `.changeset/livelocale-1-0-0.md` (section 6).

### 3.2 Non-breaking: recommended, not applied (they change code paths, so they get their own PRs)

- **Possible double start of the in-page client.** `livelocale/react` bundles its own copy of the
  client (`tsup` runs with `splitting: false`), and the start guides also import
  `livelocale/client`. Inside the Studio both copies may start, with two bridges and two click
  handlers. Read from the code, not reproduced. Fix: a once-guard on `window`, or have the
  provider import the `livelocale/client` specifier. Worth doing before the launch.
- **Studio `ERROR` message:** the Studio reads `payload.error` without a check, so a future client
  sending a bare `ERROR` would throw in an old Studio. Add the check now.
- **CLI:** add `--version`; stop the global `--help` check at `--` (today
  `livelocale build -- next build -h` prints help instead of building); reject a non-number
  `studio --port`.
- **Export the `LiveLocaleHandler` type** from `livelocale/server` (it is returned but cannot be
  named; an earlier changelog entry already lists it as a public name).
- **Packaging:** point `require()` users at the `.d.cts` types tsup already emits; pin a tsup
  build `target` so a tool upgrade cannot quietly drop Node 18.
- **Formats:** `addLocale` writes `{}` with no trailing newline while every other write adds one;
  a manifest with `format: 2` shows "missing" instead of "made by a newer LiveLocale"; add a
  `version` field to `?action=info`; add a comment in `src/core/validate.ts` that its rules are
  part of the `lc1.` format.
- **Docs:** document `?locale=`, `?livelocale-origin=`, the full `manifest.json` field list, the
  exit codes of `apply --github-event` and of `build`'s own errors, the rule that Server
  Components must import helpers from `livelocale/server` (the `/client` entry is a client
  module), and that the deployed-platform guard list may grow.
- **Phones (the headline):** the phone tests run Android emulation in Chromium only. Before
  tagging, the real-phone check should open a share link in iPhone Safari. Adding a WebKit iPhone
  project for `tests/e2e/studio-phone.spec.ts` is the cheap automated follow-up.

### 3.3 Breaking: needs your decision

Each of these would break someone, so each is your call. For each one there is an option that
breaks nobody.

1. **Remove the 22 undocumented exports** instead of only tagging them.
   - Why: tagged exports still show up in editors, and anyone using them would be broken by a
     later change, even if semver allows it.
   - Who it breaks: only people importing names no docs page mentions. Two were announced in old
     changelogs (`FileMutatorOptions`, `KeyScanner`'s scan for tooling).
   - Non-breaking option (applied): keep them with `@internal` and the stability page.
   - Recommendation: keep the tags for 1.0; remove them in 2.0.
2. **Make every command reject unknown flags.**
   - Why: `check`, `doctor`, `migrate`, `init` and `studio` ignore a mistyped flag.
     `check --strictt` passes with exit 0, so a typo quietly turns a CI check off. `apply`,
     `pack` and `build` already refuse. Same family: `apply --branches` without
     `--github-event` (ignored today) and `init --share my-app` (the folder is ignored today).
   - Who it breaks: scripts that pass a flag which does nothing. Every command line `init`
     writes into users' `package.json` uses known flags; that must be tested.
   - Non-breaking option: print a warning but keep exit 0. It does not fix CI, so it is the
     weaker choice.
   - Recommendation: do it in 1.0. It is the only change here worth breaking for.
3. **`check` exit code 2 for every "could not run" case** (missing locales folder, unknown
   `--source`, missing `--dir`), not only for missing TypeScript, and print a JSON report on
   failure with `--json`.
   - Who it breaks: a script that tests for exactly exit 1. Unlikely.
   - Non-breaking option: keep today's codes and document them as they are.
   - Recommendation: do it in 1.0, together with item 2.
4. **`migrate` exits 1 when a file failed to convert** (today it exits 0).
   - Who it breaks: almost nobody; it is a one-off interactive command.
   - Non-breaking option: document exit 0.
   - Recommendation: do it in 1.0 if items 2 and 3 are done; otherwise skip.
5. **Node.js 20 minimum instead of 18.**
   - Why: CI tests Node 20 and 24 only. Node 18 is past end-of-life. A floor can only be raised
     for free at a major version.
   - Who it breaks: Node 18 users. npm only warns, but Yarn 1 and `engine-strict` setups fail to
     install.
   - Non-breaking option: keep `>=18` (your rule in CONTRIBUTING.md) and add a CI job that runs
     the packed CLI and imports each entry on Node 18. The code uses nothing newer than Node 18.
   - Recommendation: keep 18 and add the Node 18 job.
6. **Rename `createTranslations`'s `localesDir` to `localesPath`** to match the handler and the
   Vite plugin.
   - Who it breaks: every Next.js setup in the README, the start guide and the agent skill.
   - Non-breaking option: keep `localesDir`; add `localesPath` as a second name in any 1.x.
   - Recommendation: do not rename. Keep `localesDir`.
7. **Cap the TypeScript peer at `<7`.**
   - Who it breaks: projects on TypeScript 7 could not install livelocale at all (npm treats it
     as a conflict), although only `check --hardcoded` and `migrate` need TypeScript.
   - Non-breaking option (applied): keep `>=4.7`; the docs say 4.7 to 6, and the CLI already
     explains TypeScript 7.
   - Recommendation: do not cap.
8. **Type `liveLocaleVite()`'s result as Vite's `Plugin`.**
   - Why: today its type lists every internal hook, so changing a hook could count as breaking.
   - Who it breaks: only code that calls the plugin's hooks by hand. Using it in `plugins: [...]`
     keeps working.
   - Recommendation: do it in 1.0; the risk is tiny.

## 4. Compatibility of data formats, and the tests that prove it

| Format                                     | How it is versioned                                                             | Unknown data                                                  | Proof                                                                                                                                                                                                                                                                                               |
| ------------------------------------------ | ------------------------------------------------------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `lc1.` change links                        | In the prefix: `lc1.`; `lc2.` would be reported as "made by a newer LiveLocale" | Unknown top-level fields are ignored                          | New: `tests/unit/compat-0.12.1.test.ts` decodes 4 links made by the 0.12.1 encoder (repo and no repo, forced edit, new key, note with a newline, Arabic and Japanese text, SHA-1 and SHA-256 base), in an issue body and inside an Outlook SafeLinks URL, with both the browser and the CLI decoder |
| Links from new Studios read by old Actions | Workflows pin the livelocale version, so a 0.12.1 Action reads 1.x links        | The 0.12.1 reader rejects new tuple slots and a different `v` | New: the same test checks that today's encoder writes byte-for-byte the JSON 0.12.1 wrote                                                                                                                                                                                                           |
| `manifest.json`                            | `format: 1`                                                                     | Unknown fields ignored; `pages` optional                      | New: real manifests from 0.12.1 `pack` (with and without the repo), one without `pages` (0.9 to 0.11 shape), an extra unknown field, and the drafts scope                                                                                                                                           |
| `flag.js`                                  | Signature line `/*! livelocale flag v1 */`                                      | n/a                                                           | New: today's `flag.js` must equal the one 0.12.1 deployed                                                                                                                                                                                                                                           |
| Studio-to-page messages                    | Not versioned: unknown messages and fields are ignored; READY lists `features`  | Ignored on both sides                                         | Existing unit tests only; a recorded 0.12.1 message sequence is a recommended follow-up                                                                                                                                                                                                             |

The fixtures were made from the `v0.12.1` tag: the links by `src/core/change-link.ts` at that tag,
the manifests and `flag.js` by `livelocale pack` (unchanged since the tag). They must never be
regenerated. If the test fails, the change broke a shipped format and belongs in `lc2.`, manifest
format 2 or `flag v2`.

The rule for `lc1.` within 1.x: only new optional top-level fields. No new edit slots, no new
required fields, no new limits, no stricter or looser field rules. Anything else is `lc2.`.

## 6. Release mechanics: 0.12.1 to 1.0.0

The repo uses changesets, and `publish.yml` publishes when a GitHub release is published.

1. Done on this branch: `.changeset/livelocale-1-0-0.md` with a `major` bump.
   `npx changeset status` reports livelocale for a major bump, which from 0.12.1 is 1.0.0.
2. `npm run version`. It sets `package.json` to 1.0.0 and writes a changelog block. Then by hand:
   merge the `[Unreleased]` entries (phones, English-only Studio) into a `## [1.0.0] - <date>`
   section in the house format (`### Major Changes` / `### Minor Changes`).
3. Set `plugins/livelocale/.claude-plugin/plugin.json` to 1.0.0 (a test enforces the match) and
   change `SECURITY.md` to "1.x: Yes, < 1.0: No".
4. Optional, recommended: run `publish.yml` by hand with `prerelease_base=1.0.0` to get
   `1.0.0-next.N` on the `next` tag, and do the iPhone check on it.
5. Commit `chore: release 1.0.0`, merge.
6. You create the GitHub release `v1.0.0`; `publish.yml` publishes to `latest` with provenance.

Nothing on this branch was published, tagged or pushed.
